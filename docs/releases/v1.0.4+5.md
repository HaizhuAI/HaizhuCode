# v1.0.4+5 — CRLF-in-payload hotfix

A Windows checkout produced byte-identical-but-broken payloads: files
checked out with `core.autocrlf=true` carry `\r\n`, and those bytes were
embedded verbatim into phone-side scripts and shells.

## Impact found

- The embedded `hz` CLI shipped in the bundle as `#!/bin/sh\r` — every
  `hz` command on a managed phone failed with `bad interpreter`. This
  affected the 1.0.x builds produced from this Windows working copy.
- `lib/termux/bridge.dart` and `lib/termux/opencode_ubuntu_setup.dart`
  were also `w/crlf`: raw `r'''` shell literals inside Dart sources
  inherit the worktree's line endings, so manager/setup scripts could
  carry `\r\n` onto devices in local Windows builds. CI builds (ubuntu,
  LF checkout) were unaffected — the hazard hit local/sideloaded builds.

## Fixes

- `tool/gen_haizhu_bundle.py` — every UTF-8-decodable payload file is
  normalized CRLF→LF before base64 embedding. Verified: bundled `hz` is
  now 29,059 bytes with **zero** `\r` bytes and a clean `#!/bin/sh`
  shebang.
- `.gitattributes` — `haizhu/**`, `*.dart`, `*.sh` are pinned
  `text eol=lf`; the whole worktree (1,670 files) was renormalized to
  LF. A stale-CRLF `LICENSES/*.txt` normalized along the way.
- `test/builtin_linux_test.dart` — the manager-script golden normalizes
  `\r\n`→`\n` before hashing so the drift gate is platform-stable
  (constants refreshed to the LF values: length 57328); the
  project-folder test (POSIX-absolute-path API + real `sh`) skips on
  Windows.

## Verification

- Bundle byte audit: `hz` decodes with `#!/bin/sh` and zero `\r`.
- `flutter test test/builtin_linux_test.dart`: **25/25 pass** (1
  POSIX-only test skipped on Windows) — was 2 failures before.
- `git ls-files --eol` confirms `w/lf` across the tree; the CRLF hazard
  class is closed at checkout time, not just at bundle time.
